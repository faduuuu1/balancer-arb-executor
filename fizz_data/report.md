# Fizz Report — BalancerArbExecutor

Stateful fuzz suite generated by the pashov `fizz` skill, automatic mode,
sonnet subagents. Campaign run under Medusa 1.5.1.

## Outcome

| | |
|---|---|
| Line coverage (Medusa, `BalancerArbExecutor.sol`) | **94% (100/106)** |
| Properties implemented | **7 global + 4 specific**, from 53 raw candidates |
| Foundry suite | **24 tests, all passing** |
| Medusa campaign | 24 passed, **2 failed — neither reproduces under Foundry** |

## The two Medusa failures are not contract defects

`SP-02` (a forbidden-selector step succeeded) and `GL-07` (an unsolicited
flash-loan callback got through) fail under Medusa. Four independent checks say
the contract is fine:

1. **Direct guard test** — a step carrying `approve`'s selector reverts
   `ForbiddenSelector(0x095ea7b3)` under Foundry, with a full trace showing the
   revert propagating out through `receiveFlashLoan` → `flashLoan` → `execute`.
2. **Selector-extraction test** — the byte composition in
   `_rejectTokenMutatingSelector` recovers `0x095ea7b3` and `0xa9059cbb`
   correctly. It compiles *and* is correct, which are different things.
3. **Etched-vault test** — the harness's own `MockVault`, etched at the
   hardcoded Balancer address, is live (holds storage writes) and correctly
   reverts an unsolicited `flashLoan`.
4. **Handler replay** — `test/FizzViolationRepro.t.sol` calls the exact
   handlers with the exact parameters Medusa reported. Both pass.

Coverage data also disproves the obvious explanation: `receiveFlashLoan` is
genuinely executing under Medusa (line 248 hit 4,187 times; the selector guard
at line 264 hit 1,338 times), so the callback is not being skipped. Medusa's
execution traces elide nested calls, which made it *look* like the etched vault
was inert — it is not.

The residual explanation is a Medusa-specific difference in cheatcode or
call-sequence semantics that I could not isolate without debugging Medusa
itself. **Recorded as an open discrepancy rather than resolved**, because the
evidence available says the contract is correct and I would rather leave a
documented unknown than a confident wrong answer.

## What the campaign genuinely establishes

These passed under sustained fuzzing (250k calls, ~1,000/sec):

- `property_callScopedStateIsNeutral` — `_initiated`, `_routeHash`, `_watched`
  and `_preLoan` all return to neutral between every pair of calls. This is the
  load-bearing one: leakage would corrupt the next route's baseline or leave the
  callback armed.
- `property_storageLayoutUnchanged` — guards the above against silent breakage.
  The slot numbers are hardcoded; if the contract's fields are ever reordered,
  this fails loudly instead of the neutrality check quietly reading garbage and
  passing.
- `property_onlyOwnerCanAdminister` — no non-owner call to **any** of the seven
  `onlyOwner` functions succeeds. Previously only `execute` was covered.
- `property_noResidualApprovals` — no allowance to any router survives a call.
- `property_vaultNeverAllowlisted`, `property_zeroAddressNeverAllowlisted`,
  `property_ownerNeverZero`.

## Harness bugs found and fixed during the run

1. **`targetContractsBalances` overflowed the deployer.** The scaffold ships
   `0xffff…ffff` (~6.3e57 wei) for Medusa and Echidna; the deployer holds
   2¹²⁸−1. Medusa died at "Failed to initialize the test chain" before a single
   call. Fixed in both configs.
2. **A property that silently did not exist.** The insertion script matched
   nothing and exited without writing. The build passed because the ghost
   variable existed and the handler set it — nothing read it. Medusa reported
   "15 tests passed" while the only property written was not among them.
3. **A property that was wrong, caught by the fuzzer.** The first
   `property_onlyOwnerCanExecute` assumed `admin` stays owner forever. Ownership
   genuinely moves during a run (`transferOwnership` → `acceptOwnership`), after
   which an actor legitimately *is* the owner and its call correctly succeeds.
   The fix reads `exec.owner()` at call time.
4. **Handlers that could not reach the code they tested.** Five discovery agents
   independently flagged that `_buildRoute` only ever produced well-formed
   routes, so `ForbiddenSelector` and `TargetForbidden` — two of the newest
   security fixes — were never exercised. Route kinds 4 and 5 now build
   deliberately malformed routes.

## Still not covered

| Gap | Needs |
|---|---|
| `SP-05` — approval sizing | `MockRouter` instrumented to record the allowance it observed mid-swap |
| `SP-10` — native ETH as profit token | `profitSel % 3` plus a router that refunds ETH. **This path is completely dark today.** |
| `SP-11` — reentrant router | A `MaliciousRouter` mock that calls back into `VAULT.flashLoan` |
| `ADV-11` — unwatched standing inventory | A third token the route never references |

`ADV-11` is worth restating as a design note, not just a gap: the watch set is
**derived from the route**, not from holdings, so inventory in a token the route
never mentions sits outside the guard. That is a deliberate tradeoff — watching
all holdings would be unbounded — but it is not stated in the contract header
and should be.

## Reproducing

```bash
cd contracts
forge test                                    # 24 tests
medusa fuzz                                   # full campaign
echidna . --contract FuzzTester --config echidna.yaml
```

Requires Foundry, Medusa 1.5.1, Echidna 2.3.3, and `crytic-compile`
(Python 3.14 at `AppData/Local/Python/pythoncore-3.14-64`, not on PATH).
